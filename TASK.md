# Техническое задание: Система бронирования переговорок «RB-automatics»

## 1. Общее описание проекта
**RB-automatics** — это внутренний корпоративный сервис для автоматизации бронирования переговорных комнат. Система позволяет администраторам гибко настраивать графики доступности помещений, а сотрудникам — бронировать фиксированные 30-минутные интервалы (слоты) без конфликтов и пересечений.

Система поддерживает:
- регистрацию и авторизацию пользователей;
- разграничение ролей `admin` и `user`;
- управление комнатами и расписаниями для администратора;
- бронирование и отмену бронирований для пользователя;
- просмотр доступных слотов по комнате и дате.

---

## 2. Технологический стек
- **Backend:** Go, Gin
- **База данных:** PostgreSQL
- **Frontend:** React + TypeScript + Vite
- **Аутентификация:** JWT (Bearer token)
- **Инфраструктура:** Docker / docker-compose

---

## 3. Роли и права доступа
### 3.1. Admin
- Создает переговорные комнаты.
- Удаляет переговорные комнаты.
- Создает расписание доступности для комнаты.
- Просматривает все бронирования в системе (с пагинацией).


### 3.2. User
- Просматривает список комнат.
- Получает доступные слоты по комнате и дате.
- Создает бронирование слота.
- Просматривает свои бронирования.
- Отменяет собственные бронирования.

---

## 4. Модель данных

### `users`
- `id` (UUID, PK)
- `name` (VARCHAR)
- `email` (VARCHAR, UNIQUE)
- `password_hash` (VARCHAR)
- `role` (`admin` | `user`)
- `created_at` (timestamptz)

### `rooms`
- `id` (UUID, PK)
- `name` (VARCHAR, UNIQUE)
- `description` (TEXT)
- `capacity` (INT)
- `image` (VARCHAR)
- `created_at` (timestamptz)

### `schedules`
- `id` (UUID, PK)
- `room_id` (UUID, FK -> rooms.id, UNIQUE по комнате)
- `days_of_week` (INT[])
- `start_time` (TIME)
- `end_time` (TIME)
- `created_at` (timestamptz)

Ограничения:
- `days_of_week` не пустой;
- `start_time < end_time`.

### `slots`
- `id` (UUID, PK)
- `room_id` (UUID, FK -> rooms.id)
- `start_time` (timestamptz)
- `end_time` (timestamptz)
- `created_at` (timestamptz)

Ограничение:
- длительность слота ровно 30 минут.

### `bookings`
- `id` (UUID, PK)
- `slot_id` (UUID, FK -> slots.id)
- `user_id` (UUID, FK -> users.id)
- `status` (`active` | `cancelled`)
- `conference_link` (TEXT)
- `created_at` (timestamptz)

Ограничение:
- только одно **активное** бронирование на слот (уникальный частичный индекс).

## 5. API (фактически реализованные маршруты)

### Public
- `POST /auth/register` — регистрация пользователя.
- `POST /auth/login` — вход и получение JWT.
- `GET /health` — проверка состояния сервиса.

### Auth (нужен валидный JWT)
- `GET /auth/me` — данные текущего пользователя.
- `GET /rooms` — список переговорных.
- `GET /slots?room_id=<uuid>&date=YYYY-MM-DD` — слоты на дату (если дата не передана, используется текущая UTC-дата).

### Admin only
- `POST /admin/rooms` — создать комнату.
- `DELETE /admin/rooms/:id` — удалить комнату.
- `POST /admin/schedules` — создать расписание комнаты.
- `GET /admin/bookings?page=1&limit=10` — все бронирования с пагинацией.

### User only
- `POST /bookings` — создать бронирование слота.
- `GET /bookings/my` — получить свои бронирования.
- `DELETE /bookings/:id` — отменить бронирование.

## 7. Frontend-функциональность
- Экран регистрации и логина.
- Пользовательская панель:
  - просмотр комнат;
  - выбор даты и просмотр слотов;
  - создание бронирования;
  - просмотр и отмена собственных броней.
- Админ-панель:
  - создание комнат;
  - просмотр всех бронирований;
  - управление слотами/расписаниями через соответствующие формы.
---

### 8. Нефункциональные требования
- Проверка JWT для защищенных маршрутов.
- Использование индексов PostgreSQL для ускорения выборок по комнатам, слотам и бронированиям.
- Корректная обработка ошибок в формате JSON.
- Поддержка локальной разработки через docker-compose.
